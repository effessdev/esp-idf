# Why isn't this course AI-generated? 🤔

I want to be upfront about something: **this course is written and structured by a human, not blindly generated by AI.**

Why does that matter?

Because I've tried the alternative.

I previously created an embedded C course with the help of AI. Eventually, I decided to delete it. Not because AI is inherently bad, but because the resulting course had problems that I didn't want to repeat:

- **Unexplained prerequisites:** It assumed knowledge that was only introduced in later chapters.
- **Information overload:** Instead of introducing concepts gradually, it dumped large amounts of unfamiliar material on the reader.
- **Inaccuracies:** Some tool configurations and setup instructions were incorrect. This is particularly problematic in embedded development, where tools and their configurations change over time.
- **Lack of practical learning:** It wasn't structured around projects, making it difficult to connect theory with actual development.
- **Poor visual guidance:** It lacked the screenshots and visual aids that can make unfamiliar processes much easier to understand.

I realized that simply generating a lot of technically relevant content doesn't necessarily make a good course.

So I decided to approach this one differently.

## What I'm trying to achieve

### 1. No unnecessary interruptions

I want you to be able to read a chapter without constantly stopping to wonder:

*"Wait, what does that mean? Did I miss something?"*

Unlike traditional reference documentation, this is an opinionated, structured course. It's intended to be followed from the first chapter to the last, with concepts introduced in an order that makes sense.

Whenever something is needed, I'll try to explain it before or immediately after introducing it. You shouldn't have to scroll several pages ahead to understand something, only to scroll back and continue reading.

Of course, feel free to skip anything you already know!

Sometimes, I'll deliberately leave out details that aren't relevant yet, such as legacy configuration options that exist purely for backward compatibility. When I do, I'll tell you why.

For example:

*"This value exists for legacy purposes, so we don't need to worry about it right now."*

### 2. No information overload

I don't want to throw a massive code snippet at you and expect you to understand it.

Instead, I'll build your mental model first. I'll introduce the terminology, explain the underlying concepts, and then show you the code.

Whenever possible, I'll follow this progression:

1. **Start simple:** Show the shortest, simplest code that achieves the goal.
2. **Understand it:** Explain what each part does and why it's needed.
3. **Build on it:** Gradually introduce improvements and additional concepts.

The idea is to make each new step feel like a natural extension of what you've already learned, rather than an entirely new problem.

### 3. Learn by doing

Reading about embedded systems is one thing. Actually working with them is another.

That's why the course is built around practical projects. You'll write code, connect hardware, experiment with peripherals, and see the results for yourself.

I want you to understand how things work, not just memorize APIs and copy code snippets.

### 4. Accuracy matters

Embedded development involves a lot of details: toolchain versions, configuration options, hardware differences, and framework APIs.

I will do my best to verify technical information and test instructions rather than simply assuming that generated content is correct.

Of course, mistakes can still happen. If you spot one, please let me know!

## Does this mean I don't use AI?

Not at all!

I think AI is a genuinely useful tool, and avoiding it completely would be rather silly.

I use AI for several things:

- **Fact-checking:** Double-checking technical details and identifying potential inaccuracies.
- **Learning:** Exploring complex topics so I can understand them better and explain them clearly.
- **Grammar and writing:** Polishing the wording of certain sentences and paragraphs.
- **Initial drafts:** Occasionally using AI to get a starting point for an explanation.
- **Code generation:** Generating code when it helps speed up development.

The important distinction is that **AI is a tool I use while creating this course, not the author responsible for its structure, teaching approach, and final content.**

I review, revise, and take responsibility for what goes into the course.

## A final note

I'm not claiming that this course is perfect, nor am I suggesting that AI-generated content is always bad.

I simply want to create something that I'd actually enjoy learning from: a course that respects your time, introduces concepts at the right pace, and helps you build a genuine understanding of embedded systems.

That's the goal. I hope you enjoy learning with it!
